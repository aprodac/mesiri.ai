## How memory works today (from the code)

| What | Where | Value |

| Model | `provider_executions` | `gemini-2.5-flash`, ~16–18k input tokens per call |

## Problems found

**P1 — Answers (and actions) lag behind: the model replies to an earlier message.** Severity: critical.
From #14 on, almost every reply answered the previous or an even older question. It is not only the
words: the *tools* follow the old message (#1 `cancel` → `list_projects`; #3 a recall question →
`drop_ready_entries`, which silently deleted three prepared lines the person could still see on the card;
#21 → `list_projects`). The stored history is correct, so this is the model losing track of which message
is the current one in a long history (60 turns, ~17k tokens, many near-identical Q/A pairs from the
test runs, `gemini-2.5-flash`). Once one reply is off, the history itself shows mismatched Q/A pairs and
it gets worse (it did not recover in 9 turns). Same class as #7473 earlier today ("Add Mohanlal…" →
"which Rana Mart?"), which WA-163 fixed only for the open-question case. A real user with a long day of
messages, or one who repeats themselves, will hit this. Destructive actions (drop/save/change) taken on
a stale message are the worst part.

**P2 — Silent forgetting inside the same day.** Today is cut at the last 60 turns, with no marker that
anything was cut. This user had 171 turns today (test traffic, inflated), so everything before ~14:00 was
gone, including the 08:57 bricks and 09:00 project name. Taps ("(tapped Save)") and automated checks
("(the team bot's daily check)", seq 223) take turns from the same budget. Yesterday and the day before
keep only **15 turns** each: a normal working day of 20–40 messages already loses its morning by the
next day ("same as yesterday" can then mean yesterday evening only).

**P3 — When it has forgotten, it guesses.** #3 answered "Zeta Plaza" (a later project) instead of "I
can't see that far back". Nothing tells the model that the history was cut, so it treats the oldest
thing it can see as the start of the day.

**P4 — It explains its memory wrongly.** #2: "I can only see today and the two days before" — the
question *was* about today. The person learns nothing they can act on (e.g. "I can see your last 60
messages; check the dashboard timeline for this morning").

**P5 — "I have noted that" promises more than exists.** Facts told in chat (a mestri's rate, a
contractor's team size, "our cement vendor is X") live only in the 3-day history and fall out of the
60/15-turn window sooner. After that they are forgotten without warning, though the person was told
"noted". There is no durable place for such facts and no tool for them.

**P6 — Its own refusal in memory is repeated as truth, and files duplicate team tickets.** #13 refused
to keep contractor details (after accepting Suresh's in #6), and #14 — a plain recall question whose
answer was in memory — got the identical refusal and a second `tell_the_team` ticket. WA-157's
"older version" tag only covers refusals from an older tool set; a refusal made by the *current*
version is copied freely. Duplicate tickets also add noise for the team.

**P7 — It trusts only the ready list and the database, not the conversation.** #22: "not in the ready
list or saved", about a receipt that was in the loaded history (seq 283, window 219–338). Combined with
P1, the person cannot rely on it to recall what they said an hour ago.

**P8 — The day boundary is a cliff (from the code, not live-tested).** Sessions are per calendar day:
at midnight (site time) a conversation in progress drops from 60 turns to the last 15, and becomes
"an earlier day". A late-night exchange (Ilan's 23:33–00:58 on 2–3 Nov) is split across two days.

**Side findings (not memory, seen during the test):** stock shows "-240 kg of Steel" at Green Villa
(negative stock); the primer → Paint line went to Green Villa although the last report was Main Block
(possible WA-159 gap); the reply to #13 said "I have an entry ready" with no card drawn and printed
"Ref #0ae95f" to the user.

## What was not verified

- P8 (midnight) is from the code; not reproduced live.
- Whether P1 is caused by history length, by the repeated near-identical test messages, or by the model
  choice was **not** isolated (would need a fresh test user or a replay with a shorter history).
- Only one sender, one company, one session of 22 messages; not repeated 3× (the live-scenario rule).
- The test user's history is unrealistically long (171 turns today); a real user's day is shorter, so P2
  hits real users mostly via the 15-turn cap on earlier days.
